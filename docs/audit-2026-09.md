# Campaign data audit — September 2026

Two data-integrity defects had already been found by accident: patches that
never compiled scored as `fixed` (203 runs), and the word `attempted` carrying
two different denominators in the notebook. Both had the same shape — **a value
that degraded silently into something indistinguishable from a legitimate
one** — which is not a shape you find by rereading code, because the code looks
reasonable. This audit therefore recomputed every verdict from the raw
artifacts and asked where the two disagree.

Method, tooling and reproduction commands are in [§7](#7-how-to-reproduce-this).

---

## Headline

**The reported 3-point advantage of `gpt-oss:120b` over `qwen3.6:35b` does not
survive the audit.** 46 qwen runs had the model's answer dropped before it was
ever read, and were recorded as the model failing to fix the bug. `gpt-oss` has
zero such runs, so the handicap is entirely one-sided.

| Scenario for the 46 | qwen3.6:35b | gpt-oss:120b | gap |
|---|---:|---:|---:|
| As currently reported | 400 (47.2%) | 425 (50.2%) | **3.0 pts** |
| Drop the 46 bugs from both models | 400 (49.9%) | 414 (51.7%) | 1.8 pts |
| qwen fixes them at its own base rate (47%) | 422 (49.8%) | 425 (50.2%) | **0.4 pts** |
| qwen fixes all of them | 446 (52.7%) | 425 (50.2%) | −2.5 pts |

Only a re-run settles which row is true. Until then the honest statement is
that **the two models are not distinguishable on this data**.

> **Resolved by the rerun (2026-09-11).** None of the rows above turned out to
> be true, because recovering qwen's lost answers did not recover fixes. With
> every defect fixed, a 32768-token budget and all 854 bugs completed for both
> models: **gpt-oss:120b 429 (50.2%), qwen3.6:35b 396 (46.4%), a 3.9-point
> gap, exact McNemar p = 0.025** on the paired bugs. But 31 qwen generations
> still exhausted the budget; removing those bugs for both models leaves a
> 2.8-point gap at **p = 0.115**. So gpt-oss is ahead *if* a model that cannot
> finish within 32k tokens counts as failing -- and not demonstrably ahead
> otherwise. The same rerun shows each model changing its verdict on 19% of
> bugs between the two campaigns, with a net change of -7 and 0 fixes: the
> aggregate rates are stable, the per-bug verdicts are not. See
> `analysis/analysis.ipynb`, sections 4.4-4.5.

Everything else the audit checked held up. In particular the corrected fix
counts (400 / 425), the 203 non-compiling patches, and the FixCheck vacuity
analysis all reproduce exactly from the raw logs.

## 1. Confirmed defects, with measured impact

### 1.1 The model's answer was read from the wrong field — 46 runs, not repairable

`llms/ollama_llm.py` read `response.message.content` and never checked it was
non-empty. `qwen3.6` is a reasoning model: it emits its chain of thought into
`message.thinking` and the answer into `message.content`. When the token budget
ran out during reasoning, `content` came back empty, `parse_search_replace_blocks("")`
returned `[]`, `fix.diff` was written 0 bytes, and the run was recorded as
`applied: false, fixed: false` — indistinguishable from a model that had no fix.

Two distinct ceilings, cleanly separated in the data:

| Mechanism | Runs | Evidence |
|---|---:|---|
| `num_predict = 24576` reached (output cap) | 30 | `output_tokens == 24576` exactly |
| `num_ctx = 49152` exhausted (context window) | 16 | `input_tokens + output_tokens == 49152` exactly, in all sixteen |

`gpt-oss:120b` hits neither (1 run near the context ceiling, 0 lost responses)
because it is far more concise: median 1694 output tokens against qwen's 5829.
**The configuration penalises the reasoning model, and the penalty was recorded
as a capability difference.**

*Fixed*: `llms/ollama_llm.py` now inspects `done_reason`, detects both ceilings
separately, warns loudly, and records `generation_status`, `done_reason`,
`response_truncated`, `context_exhausted` and `reasoning_chars` in
`result.json`. The wrapper still never passes reasoning off as an answer —
`thinking` is not a patch — but an empty answer is now a stated fact rather than
a silent zero.

*Not repairable from disk*: the answer was never generated. These 46 runs are
the core of [`audit/rerun_manifest.csv`](../audit/rerun_manifest.csv).

### 1.2 The failing-test parser truncated at the first space — 1 wrong verdict

`parse_failing_test_names` used `re.findall(r"^\s*-\s*(\S+)")`. `defects4j test`
does not only emit `- Class::method`; a census of all 7503 such lines in the
campaign found three shapes:

| Shape | Lines |
|---|---:|
| `org.foo.BarTest::testBaz` | 7491 |
| `org.foo.BarTest` (class-level failure, no method) | 11 |
| `broken test input <FQCN><ExceptionClass>` (class would not load) | 1 |

`(\S+)` turns the third into the token `broken`, so the trigger test it was
actually reporting can never match — and `evaluate_fix` concludes the trigger
passes.

Confirmed instance, `results/gpt-oss:120b/Mockito/Bug_15`: recorded
`triggers_fixed: true` while its trigger test's class had blown up on load. It
escaped `fixed: true` only because two unrelated tests happened to regress. Its
`new_failures` list literally contains the string `"broken"`.

*Fixed*: `parse_failing_test_names` now returns only lines it can identify as
`Class::method`; `unidentified_failing_lines` and `triggers_possibly_masked`
report the rest, and `evaluate_fix` takes a `masked_triggers` argument that
forces a negative verdict rather than an optimistic one. Verified against the
real Mockito 15 artifacts: `triggers_fixed` goes `True → False`, and the
spurious `"broken"` disappears from `new_failures`.

*Repairable from disk*: yes — the re-derivation already applies the corrected
parser.

### 1.3 FixCheck was invoked on the 203 non-compiling patches, and counted as having run

`Experiment.py` gates FixCheck on `triggers_fixed`, which it computed *before*
the compile guard. So FixCheck was launched on all 203 patches that never built
and aborted on every one with `ok: false, error: "defects4j compile failed"`.
`summarize_campaign.collect_project` then did `fixcheck_ran = bool(fixcheck)`,
counting all 203 as FixCheck runs — **which is why the CLI table and the
notebook disagreed by exactly 203 on that column**, while the module docstring
claimed they could not disagree.

*Fixed*: three separate fields — `fixcheck_invoked`, `fixcheck_ran` (invoked
**and** `ok`), and `fixcheck_analyzed` — surfaced in both the CLI table and the
notebook. The qwen table now reads `invoked 561 / ran 457 / analysed 339`, and
561 − 457 = 104 is precisely qwen's share of the 203.

*Bonus*: this makes visible that `fixcheck_ran == triggers_fixed` by
construction, so that column can never fail — it looked like a validation and
was a tautology.

### 1.4 Missing measurements entered the statistics as measured zeros

`collect_project` used `fixcheck.get("analyzed_test_classes", 0)`,
`.get("failing_prefixes", 0)` and `.get("max_failure_similarity", 0.0)`. A run
where FixCheck never ran contributed a hard `0.0` similarity to the histogram
that the whole detection-power argument rests on.

*Fixed*: these are `None` when there is no measurement, and the notebook counts
the buckets explicitly, with an assertion that every plausible patch lands in
exactly one of *analysed* / *vacuous* / *no measurement*. (It currently reports
`no_measurement = 0`, so this changed no published number — but it was one
missing `fixcheck` block away from doing so.)

### 1.5 `results_dir` was never cleared, and `result.json` was written non-atomically

`Experiment.py` did `makedirs(exist_ok=True)` and nothing else, while FixCheck's
output is copied in with `copytree(..., dirs_exist_ok=True)`, which *merges*. A
retry into a directory left by a killed run would interleave two runs' generated
prefixes with nothing on disk marking it. Separately, a plain open/write/close
of `result.json` leaves truncated JSON if the process is killed mid-write — and
`experiment_runner.load_result` maps a decode error to `None`, which
`run_project.should_run` reads as "this bug never ran", re-running it into the
same dirty directory.

*Fixed*: the directory is removed before each attempt, and `write_text` writes
to a temporary file, `fsync`s, and `os.replace`s.

**This one never fired — see [§2](#2-what-the-audit-cleared).**

### 1.6 SLURM's grace period bought nothing

`--signal=B:TERM@300` delivers SIGTERM to the batch shell only, and bash defers
a trap until the foreground command returns. With `python run_project.py` in the
foreground, the run never saw the signal, `run_project`'s own
`_install_signal_handlers` never fired, and `cleanup()` — which does
`rm -rf "$WORKDIR"` — would run at an uncontrolled moment relative to it.

*Fixed*: `scripts/project_job.sbatch` now runs the job in the background,
forwards TERM to it explicitly, and waits for it to stop before tearing down the
Ollama daemon and the shared volume.

**Still open**: 300 s of grace against a 7200 s per-bug timeout means an
in-flight bug cannot finish regardless. That is a sizing decision, not a bug.

### 1.7 `preflight()` silently degraded to "no problems"

`run_project.py` never called `load_dotenv`, so with `OLLAMA_BASE_URL` unset in
the environment both of `preflight()`'s guards — the port-mismatch check and the
model-availability check — were skipped. Each child `Experiment.py` *does* call
`load_dotenv` and would then pick up `.env`'s pinned port: on a shared node,
potentially another job's daemon. The guard was disabled in exactly the case it
exists for.

*Fixed*: `run_project.py` loads `.env` itself and reports a missing
`OLLAMA_BASE_URL` as a problem rather than a reason to skip checking.

### 1.8 A failed issue fetch was recorded as "the tracker has no text"

`fetch_issue_text` caught every exception and returned `""`, which
`get_issue_text` mapped to `ISSUE_EMPTY` — a claim about the bug. A GitHub
rate-limit, a timeout or a 5xx became a permanent property of the benchmark.

*Fixed*: a new `IssueFetchError` and a new `ISSUE_FETCH_FAILED` status keep "we
could not ask" apart from "there is nothing to ask for".

### 1.9 The shared `failing_tests` path could be read stale

`run_trigger_tests_raw` runs `defects4j test -t <trigger>` for each trigger and
then reads `<workdir>/failing_tests` — a single path every invocation
overwrites. If one aborted before writing, the read returned the *previous*
trigger's trace, attributed to this one. That trace is the baseline FixCheck
measures similarity against, so a stale or empty one yields a confident wrong
verdict. The exec result was also discarded entirely.

*Fixed*: the file is removed before each invocation, the exit code is captured,
and an empty capture is warned about.

### 1.10 Off-by-one in a documented count

Three places state "**40** of the 854 bugs have no usable issue" while giving a
breakdown (22 unusable + 18 Chart empty + 1 Jsoup) that sums to **41**. Measured:
`available 813, unusable 22, empty 19` = 854. `docs/campaign.md`'s table also
said `available 814`, making its column sum to 855.

*Fixed* in `d4j/defects4j_bugs.py`, `CLAUDE.md` and `docs/campaign.md`.

## 2. What the audit cleared

Reporting these matters as much as the defects: two hypotheses that looked like
findings turned out to be false, and one of them was mine.

- **No run directory holds artifacts from more than one attempt.** The hazard of
  §1.5 is real in the code but never fired. Artifacts are written in two bursts
  — `FixGenerator` writes its three as soon as the model answers, `Experiment.py`
  writes the rest at the end — so the *gap between* the groups is just how long
  the apply/compile/test phase took (up to 97 minutes on Chart) and means
  nothing. The spread *within* each group is **0.0 s across all 1708 runs**,
  maximum included. An earlier heuristic of mine that flagged 7 directories was
  measuring run duration, not contamination.
- **The "442 `fixcheck/` directories vs 583 non-null `fixcheck` fields"
  discrepancy is not evidence of anything.** The two quantities are not
  comparable: FixCheck writes an output directory only when it produced output,
  and 216 runs have `analyzed_test_classes == 0`. Zero orphan directories were
  found.
- **The 203 non-compiling patches are exactly the set already known.** The
  re-derivation reproduces them run-for-run, and they match an *independent*
  witness on disk — FixCheck's own `ok: false, "defects4j compile failed"` —
  **203 of 203, with no case in either set alone**.
- **No violations of the structural invariants**: `fixed ⟹ triggers_fixed ⟹
  applied`, `fixed ⟹ compiled_after`, `fixcheck_suspicious ⟹ analyzed > 0`, no
  duplicate `(model, bug)` rows, no bug id outside `active-bugs.csv`, 1708 rows
  = 854 × 2.
- **The notebook's stored outputs reproduce from a fresh execution**, before and
  after this audit's changes.

One anomaly worth knowing about but harmless here: `docker_utils` merges stdout
and stderr (`demux=False`), and in `gpt-oss:120b/JacksonDatabind/Bug_33` the
output interleaved as `Running ant (run.dev.tests)....... Failing tests: 0` /
`OK`. It parsed correctly, but it demonstrates the merged stream can split
precisely the line every parser looks for. The verifier flags this
(`interleaved` column); the pipeline does not.

### 1.11 The audited campaign ran without GPU isolation (found while relaunching)

Ollama 0.32 turned its experimental Vulkan backend on by default, and **Vulkan
does not honour `CUDA_VISIBLE_DEVICES`** -- the only GPU isolation this cluster
applies, since it does not confine `/dev/nvidia*` per job. Each job therefore
enumerated all 9 GPUs and chose one by looking at free memory, so jobs launched
together could pick the same card.

Counted from the job logs: **99 of the 103 campaign jobs ran on Vulkan**, 4 on
CUDA. The audited campaign is essentially all Vulkan.

What this does and does not affect:

- **Not the verdicts.** Which GPU a generation ran on does not change the patch
  the model produced, nor whether it compiled or passed the trigger tests.
- **The timings, yes.** `seconds` per bug is contaminated wherever two jobs
  shared a card, so the median/p90 figures used to size `--minutes-per-bug` are
  upper bounds of unknown tightness.
- ~~**Very likely the 6 timeouts.**~~ **Refuted for 4 of the 6** — see §1.13.
  This section originally claimed GPU sharing was the simplest explanation for
  the archived campaign's 6 timeouts. The rerun tested it and it was wrong:
  Math 10 and 13 timed out again for *both* models on correctly isolated GPUs
  generating at 123-165 tok/s, and the job logs show 4 of the 6 archived
  timeouts dying inside FixCheck, after the patch had passed its tests. Only
  JacksonXml 2 (both models) died during generation, and remains unexplained.

*Fixed*: `scripts/ollama_serve.sh` pins `OLLAMA_VULKAN=0`, so the runner uses
the CUDA backend -- which, with §1.12's fix, sees exactly the GPU SLURM
allocated. (This paragraph first said Vulkan off was sufficient; it was not.) The `cuda_v12`/`cuda_v13` backends ship with
the same install, so this costs nothing. Guarded by a unit test, because the
symptom -- `ggml_gallocr_reserve_n_impl: failed to allocate Vulkan0 buffer` --
points nowhere near the cause.

**How it surfaced**: raising the context window to 131072 made each model
instance large enough (67.2 GiB predicted for gpt-oss) that a collision became a
hard allocation failure instead of merely slow sharing. The window change did
not cause the defect; it made a pre-existing one visible.

### 1.12 CUDA opened a different physical GPU than SLURM allocated (found during the rerun)

Turning Vulkan off was not enough. SLURM's GPU index is the `/dev/nvidiaN`
minor in `gres.conf`, i.e. **PCI bus order** -- the numbering nvidia-smi shows.
CUDA's default device order is **`FASTEST_FIRST`**, which on this mixed node
enumerates the five L40S before the four H100s. The same
`CUDA_VISIBLE_DEVICES` therefore named a different card:

| SLURM gives | `CUDA_VISIBLE_DEVICES` | CUDA opened |
|---|---|---|
| H100 `03:00.0` | 0 | **L40S `43:00.0`** |
| H100 `04:00.0` | 1 | **L40S `44:00.0`** |
| L40S `84:00.0` | 6 | **H100 `04:00.0`** |
| H100 `c3`/`c4` | 7 / 8 | H100 `c3`/`c4` (right by coincidence) |

`gpt-oss:120b` (61.7 GB) opened on a 46 GB L40S ran spilled at **~0.5 tok/s
instead of ~130**, and five of its rerun jobs hit SLURM's wall clock with
almost nothing done (Time: 2 of 26 bugs in 7.5 h). Jobs also landed on cards
SLURM had given to *other* jobs -- ours and, potentially, other users' -- and
when a load found its card full, Ollama put the model on the CPU, where the
persistent runner kept it for every later bug (`offloaded 0/42 layers to GPU`,
~160 cores).

**The smoke test that "validated" the relaunch was one of these runs.**
gpt-oss Lang 1 ran at 2.5 tok/s on an L40S; its 1163 s were read at the time as
model loading. Only `library=CUDA` was checked, not which card nor how fast.

*Effect on results*: verdicts are unaffected (the device does not change
whether a patch compiles and passes). Completed rerun runs: gpt-oss 668 on the
right card type and 26 on an L40S; qwen 676 on the right type and 70 on an
H100. **Timings are not usable** for those 96, and are unreliable in general
for this campaign -- use token counts, not seconds, as the cost measure.

*Fixed*: `CUDA_DEVICE_ORDER=PCI_BUS_ID` in `scripts/ollama_serve.sh`, verified
by matching the PCI id Ollama reports against nvidia-smi's for the allocated
index (the formerly broken H100 index 1 now opens H100 `04:00.0` at 172.7
tok/s), plus a unit test. And `run_project.py` now checks `/api/ps` before
every bug and aborts the job (exit 3) if the model is resident but not fully in
VRAM, so a CPU fallback can no longer continue silently for a whole job.

### 1.13 A hung FixCheck destroyed a verdict that had already been computed

FixCheck runs its mutated test prefixes with no timeout of its own, and
role-blind mutation of an `int` can make one effectively unbounded. When that
happened the per-bug timeout killed the whole run -- and since `Experiment.py`
wrote `result.json` only *after* FixCheck, **the patch's verdict was lost** even
though it had already been computed.

From the job logs, every timeout in both campaigns classified by the phase it
died in:

| Campaign | Died in FixCheck (verdict computed, then lost) | Died in generation |
|---|---|---|
| Archived | gpt-oss Compress 47, Math 13, Math 31; qwen Math 10 | JacksonXml 2 (both) |
| Rerun | Math 10 and 13, both models | 7 runs on the wrong device (§1.12) |

In three of the archived four the log reads `Failing tests after fix: 0`:
**they were correct fixes recorded as "no result"** (gpt-oss Compress 47 and
Math 13, qwen Math 10). They dropped out of the paired set, which therefore
excluded bugs where a model had *succeeded* -- a small (≤4 bugs) selection
effect on the archived comparison.

*Fixed*, in two layers:

1. FixCheck gets its own budget (`--fixcheck-timeout`, default 1800 s per
   trigger class, twice the measured p99), enforced with coreutils `timeout`
   inside the container. A stop is recorded per class as `timed_out` and at
   the top level as `timed_out_test_classes`; the verdict counts as vacuous
   (`analyzed_test_classes == 0`), never as evidence.
2. `result.json` is written **before** FixCheck starts, carrying a
   `FIXCHECK_PENDING` marker (`ok: false, pending: true`) that FixCheck's real
   result then replaces. Anything that interrupts FixCheck can now cost only
   FixCheck's block.

Verified on gpt-oss Math 10: `result.json` was on disk with `fixed: true` 21
minutes into FixCheck; FixCheck was stopped at 1800 s; the run completed as
`ok`, `fixed: true`, in 33 min.

## 4. Still open, deliberately

- **The 54 runs in `audit/rerun_manifest.csv`** (46 lost responses + 8 killed
  runs with no `result.json`). ~16 GPU-hours at the previous runs' durations,
  more in practice since a successful generation runs longer. **The decision on
  whether to re-run is yours** and was deferred to this point on purpose.
- **The generation budget itself.** Re-running without raising `num_predict` /
  `num_ctx`, or without asking Ollama to separate reasoning from the answer,
  would reproduce the same 46 failures. This is a configuration decision, not a
  code fix.
- **300 s of SLURM grace against a 7200 s per-bug timeout** (§1.6), and
  `runCampaign.sh` sizing wall clock at 20 min/bug while the timeout allows 120.
- **`FixGenerator._resolve_source_path`**: when a bug has exactly one source
  file, *any* unresolvable path the model names resolves to it. Now recorded
  (`blocks_parsed` / `blocks_applied` / `blocks_failed` reach `result.json`), not
  yet prevented.
- **No standing invariant test suite.** The invariants in §2 were checked once,
  during this audit. Nothing re-checks them.

## 6. A note on the shape of these defects

Nine of the ten are the same mistake: **a value that could not be measured was
given a default that a measured value could also have had.** `-1` for an absent
count. `""` for a failed fetch. `0` for an absent similarity. `False` for a
missing key. The empty string for a response read from the wrong field.

None of them look wrong at the call site. They look defensive. What makes them
dangerous is that the resulting value is *plausible*, so nothing downstream
raises, and the number reaches a table looking exactly like a real one.

The one structural defence is to keep "not measured" in the type — which is why
`audit/rederive.py` has an `UNKNOWN` that raises `TypeError` on `bool()`, and
why `collect_project` now returns `None` rather than `0`.

## 7. How to reproduce this

The audited campaign has since been archived to `results/old/9-Sep/`, so the
commands take an explicit `--results-dir`:

```bash
# Recompute every verdict from the raw artifacts and diff against result.json.
.venv/bin/python -m audit.rederive --results-dir results/old/9-Sep
.venv/bin/python -m audit.rederive --results-dir results/old/9-Sep --divergences

# Census the artifacts and flag incoherent run directories.
.venv/bin/python -m audit.inventory --results-dir results/old/9-Sep

# The runs that cannot be repaired from disk.
column -s, -t audit/rerun_manifest.csv

.venv/bin/python -m pytest test/unit -q         # 205 passed
.venv/bin/python summarize_campaign.py --results-dir results/old/9-Sep \
    --model ollama/qwen3.6:35b
```

`audit/rederive.py` imports nothing from `Experiment.py` on purpose: it is a
second opinion, and a second opinion that shares the first one's parser is not
one. Its own parsers are pinned by `test/unit/test_audit_rederive.py` against
the real malformed shapes found in the campaign's logs.
